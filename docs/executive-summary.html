How GEMSDOE32 got 0.2778, and can we beat it?

GEMSDOE32's h33-h33-2-b2 (0.2778 OWNER-REPORTED) is the highest of the nine pinned owner/user-reported numbers, but no organizer submission-page receipt exists, so it is not ORGANIZER-CONFIRMED.

The file is byte-identical, within the footprint, to the GEMSDOE25 / GEMSDOE30 D2.8 mask (44,090 dots) with dots removed near the catalogue:

  • GEMSDOE25/30 D2.8 → 44,090 dots → 0.2600
  • GEMSDOE28/31 solo (d2.8 minus dots ≤1 px from catalogue) → 40,199 dots → 0.2708
  • GEMSDOE32 B2 (solo minus dots ≤2 px from catalogue) → 37,654 dots → 0.2778

Why it helped: dots within ~200 m of a mapped catalogue fault pay the 0.2 false-positive penalty in the DTI denominator but earn almost no true-positive credit (organizers mask known faults pixel-exactly; new truth can lie close by). Pruning the dead 0–2 px annulus removes denominator mass without removing numerator credit, so the score rises. The gain is deletion of low-credit dots, not new geology.

Can we beat 0.2778? Not with anything validated here. The arithmetic (from docs/research/why-02778.md) says beating 0.30 needs ~+8 % more true-positive credit per dot; beating the verified public leaderboard top (~0.44) needs ~+59 %. That requires a better detector of off-catalogue faults — more dots on truth, fewer on dead annulus — not more emission tricks. No labels.tif is available to validate a holdout DTI, so no score is claimed for the new candidate below.

Labeling rule: every number is either HOLDOUT-DTI (evaluator version, withheld positives, 95% CI) or owner/user-reported (no receipt). A projection is never written as a score. The GEMSDOE32 0.2778 figure is owner-reported and cannot be tied to exact uploaded bytes.

Submission guide

How to make a submission into the contest

DrivenData accepts a single-band GeoTIFF (.tif) or a .zip containing a single GeoTIFF. It must match the submission format's CRS, shape, and geotransform. Predicted values must be in range [0, 1] — a prior portal rejection was "Predicted values must be in range [0, 1]", which happens when NaN appears outside the footprint; the zeros variant below avoids it by writing 0 outside and nodata=None.

  1. Get the official template

    Download sample_submission.tif from the competition data tab (DrivenData login required). It pins EPSG:32611, 3730×3292, 100 m geotransform.

  2. Produce predictions

    Generate a 3730×3292 single-band float32 array in [0,1] over the footprint. Sanitize NaN/Inf (NaN→0, clip to [0,1]). Do not copy a previous submission byte-for-byte; check uniqueness (|Spearman rho| ≤ 0.90 and ≤ 70% of dots within 3 px of any registry raster).

  3. Write the GeoTIFF

    Use the template's own raster profile (CRS, shape, geotransform, float32, one band). Write nodata=None with 0 outside the footprint (zeros variant) — this keeps every cell finite and in [0,1]. Optionally ZIP the single GeoTIFF.

  4. Validate locally

    Run python scripts/validate_submission.py yourfile.tif --template sample_submission.tif. Confirm: single band, EPSG:32611, shape 3730×3292, geotransform match, all cells finite and in [0,1], no NaN inside the footprint.

  5. Name and note

    Give the submission a unique name on the DrivenData form and a short comment (≤140 characters) that tells your team what it is, e.g. clustering with k=25. Example note: GEMSDOE36 lattice-avoiding off-catalogue dots | 505 dots | research candidate | id 6e268a98cbf3.

  6. Upload

    Go to the submission page, choose the .tif or .zip, add the note, and submit. Official rules allow three weekly slots and one submission for both prize rounds; check the rules PDF and the competition deadline.

This page does not auto-upload: DrivenData authentication is required and is intentionally not handled here. The generated TIF above is provided for download so you can upload it yourself once you judge it ready.
