## Why placement stopped

The pinned, registered 13GEMSDOE 5-pixel lattice (`reg-052`, SHA-256 `b4570b406efec198eb2f4d142ad8d0d6184b14b66f2f52b5c4d697f0647dc9b2`) has **206,895 positive pixels**. In the SHA-verified sample-template footprint of **5,167,373** pixels, exactly **5,160,724** are within Euclidean distance ≤3 pixels of a lattice dot. Only **6,649** are farther away. These are owner-provided mirrors, not independently authenticated organizer downloads.

For any `K` distinct candidate pixels in that footprint, at least `max(0, K − 6,649)` must be within 3 pixels of this one registered raster. For the historically matched budget `K = 37,654`, at least **31,005 / 37,654 = 82.34185%** overlap; the user's stop is **strictly greater than 70%**. This is a mathematical lower bound, not a measured score and not a statement about geological similarity. The bound first exceeds the limit at **22,164** dots. Equality at 70% does not fail the stated strictly-greater-than rule. A smaller output is *not* automatically unique: all rank and dot comparisons still apply. The rule requires stopping, not exempting calibration controls or moving dots into uncovered holes.

Reproduce after restoring the pinned mirrors:

```bash
python scripts/restore_data.py --group core
python scripts/restore_data.py --group scored
python scripts/registry_feasibility.py --dots 37654  # exit 2 = proven duplicate, 0 = NOT proven, 1 = input error
```

The preflight checks hashes, geometry and the registry footprint digest, and reuses `gems.novelty.classify_space_filling_control`; it does **not** run or replace the required full surface/point registry comparisons. A no-proof result is not a pass. Input inconsistencies fail closed. [Regression tests](../../tests/test_registry_feasibility.py) exercise the strict boundary, bad inputs and the real pinned lattice.
